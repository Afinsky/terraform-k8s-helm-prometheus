Принципы, из которых выведена структура

Каждое решение по дереву каталогов ниже — следствие одного из этих пяти правил. Если возникнет вопрос «а можно иначе» — сверяйтесь с этим списком, а не с интуицией.

Каталоги, не ветки

Окружение — это папка (overlays/prod), а не git-ветка. Ветки для окружений расходятся и требуют болезненных merge; папки в одной ветке — просто диффятся.

ApplicationSet, не Application

Ни одного ArgoCD Application не создаётся руками. Все они — продукт генератора поверх файловой структуры. Новое приложение = новая папка, не новый YAML для Argo.

Git — единственный источник правды

Ни kubectl edit, ни ручной helm upgrade. Если ресурса нет в git — считаем, что его не должно быть в кластере (self-heal это обеспечивает).

Секретов в git нет

Ни в открытом виде, ни зашифрованными «на всякий случай». Ссылка на секрет — да, значение — никогда.

CI проверяет форму, CD — доставляет

Валидность YAML, политики и линтеры — это pull request. Синхронизация с кластером — это ArgoCD. Смешивать эти две роли в одном пайплайне не стоит.

02

Bootstrap — единственный шов между Terraform и Argo

Terraform ставит ArgoCD как обычный helm_release (он не отличается от других контроллеров в репозитории — тот же паттерн IRSA, тот же depends_on). Дальше Terraform создаёт ровно один дополнительный объект — корневой Application, указывающий на gitops/bootstrap/root.yaml. С этого момента Terraform больше никогда не создаёт и не меняет ничего внутри gitops/ — это единственная точка передачи ответственности.

gitops/bootstrap/root.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/<org>/terraform-k8s-helm-prometheus.git
    targetRevision: main
    path: gitops/clusters/develop
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

Дальше root раскрывает два ApplicationSet из clusters/develop/ — а они уже рекурсивно разворачивают всё остальное. Ручных kubectl apply после первого bootstrap быть не должно.

03

Clusters/ и генераторы ApplicationSet

Каждая ApplicationSet использует git generator directories — она сканирует папку и создаёт один Application на каждую найденную подпапку. Добавить компонент = создать папку. Ничего в Argo-конфиге редактировать не нужно.

gitops/clusters/develop/platform-appset.yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: platform-develop
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - git:
        repoURL: https://github.com/<org>/terraform-k8s-helm-prometheus.git
        revision: main
        directories:
          - path: gitops/platform/*
  template:
    metadata:
      name: "platform-{{.path.basename}}-develop"
    spec:
      project: platform
      source:
        repoURL: https://github.com/<org>/terraform-k8s-helm-prometheus.git
        targetRevision: main
        path: "{{.path.path}}"
      destination:
        server: https://kubernetes.default.svc
        namespace: "{{.path.basename}}"
      syncPolicy:
        automated: { prune: true, selfHeal: true }
        syncOptions: [CreateNamespace=true, ServerSideApply=true]

apps-appset.yaml — зеркало этого файла, только path: gitops/apps/* и project: apps. Два генератора, две зоны ответственности, одна и та же механика.

04

platform/ — add-on'ы кластера

Каждый контроллер, который сегодня описан связкой «aws_iam_role + helm_release» в одном .tf-файле, разделяется на две половины:

  • Terraform оставляет себе IAM-роль и создаёт голый kubernetes_service_account_v1 с аннотацией eks.amazonaws.com/role-arn — без Helm.
  • ArgoCD получает чистый Helm-чарт из platform/<name>/, где values-base.yaml задаёт serviceAccount.create: false и serviceAccount.name: <то же имя>.

Ни один YAML в gitops/ не содержит terraform-вычисляемых значений — граница получается буквальной, не «по договорённости».

gitops/platform/external-dns/application.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: platform-external-dns
  namespace: argocd
spec:
  project: platform
  sources: # multi-source: чарт из upstream, values — из этого репо
    - repoURL: https://kubernetes-sigs.github.io/external-dns/
      chart: external-dns
      targetRevision: 1.21.1
      helm:
        valueFiles: [$values/gitops/platform/external-dns/values-base.yaml,
                     $values/gitops/platform/external-dns/values-develop.yaml]
    - repoURL: https://github.com/<org>/terraform-k8s-helm-prometheus.git
      targetRevision: main
      ref: values
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    retry: # see §08 — ordering vs. LB Controller/ingress-nginx is retry, not sync-wave
      limit: 5
      backoff: { duration: 10s, factor: 2, maxDuration: 3m }

Upstream-чарты используются напрямую по версии, без форка — форк оправдан только когда нужно патчить шаблон чарта, а не значения (тогда добавляется Kustomize post-renderer поверх Helm-вывода). Ни source:, ни sync-wave-аннотация здесь больше не стоят рядом с sources: — см. поправку в §08: для независимых, сгенерированных ApplicationSet'ом Application'ов эта аннотация ничего не упорядочивает.

05

apps/ — Kustomize base + overlays

Для собственных приложений (в отличие от upstream-чартов) — Kustomize, не Helm: манифесты простые, шаблонизатор не нужен, а base/ + overlays/<env> даёт ровно то различие между окружениями, которое требуется — реплики, домен, лимиты ресурсов — без дублирования всего YAML.

gitops/apps/photoapp/overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
patches:
  - target: { kind: Deployment, name: photoapp }
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 5
  - target: { kind: Ingress, name: photoapp }
    patch: |-
      - op: replace
        path: /spec/rules/0/host
        value: myapp.abotyan.click
images:
  - name: photoapp
    newName: <account>.dkr.ecr.us-east-1.amazonaws.com/me
    newTag: v1.4.2 # никогда :latest — см. промоушен ниже
06

AppProject — граница RBAC, а не формальность

Без AppProject любой, кто имеет доступ к ArgoCD, может задеплоить что угодно в любой namespace. Два проекта разводят «инфраструктуру» и «приложения» так же, как это разведено в platform/ и apps/ — доступ и структура каталогов зеркалят друг друга.

AppProjectsourceReposdestinationsкто
platformэтот репозиторий + upstream helm-репо контроллеровлюбой namespace, cluster-scoped ресурсы разрешеныинфра-команда
appsэтот репозиторийтолько namespace приложений, без cluster-scopedapp-команды

Именно эта граница — то место, где RBAC перестаёт быть «доверием на словах»: app-команда физически не может создать ClusterRole через свой Application, даже если попытается.

07

Секреты: ничего не меняется, просто применяется последовательно

В репозитории уже есть External Secrets Operator, читающий AWS Secrets Manager — этот механизм переносится в gitops/ без изменений: ExternalSecret лежит рядом с Deployment в apps/photoapp/base/, значение секрета никогда не попадает в git, туда попадает только ссылка на него (remoteRef.key).

Правило без исключений

Если для какого-то нового компонента ESO не подходит (например, статичный non-secret конфиг, который всё же не хочется светить публично) — используется SOPS с шифрованием через тот же путь IAM/KMS, что уже есть в проекте. Base64 в ConfigMap/Secret — не вариант ни при каких обстоятельствах, это не шифрование.

08

Sync policy и порядок волн

Сегодня порядок разворачивания задан явными depends_on в Terraform. В GitOps-мире напрашивается прямая замена — аннотация argocd.argoproj.io/sync-wave — но у неё есть ограничение, которое стоит проговорить прежде, чем на неё опираться.

Поправка по факту реализации

sync-wave упорядочивает ресурсы внутри одного Application — то есть работает между источниками одного multi-source Application (см. external-secrets ниже), и работает между дочерними Application'ами настоящего app-of-apps, где родитель применяет их как собственные ресурсы своего sync. Application'ы, которые порождает ApplicationSet (все platform-* из §04), — независимые top-level объекты, не ресурсы чьего-то sync, поэтому аннотация на них попросту ничего не упорядочивает, даже если выглядит рабочей.

Отсюда — два разных механизма для двух разных ситуаций:

Что упорядочиваемМеханизмПример
Ресурсы внутри одного Applicationsync-wave на ресурсеCRD чарта external-secrets (волна 0) → ClusterSecretStore (волна 1), см. §07
Независимые platform-* Application'ыsyncPolicy.retry с backoffingress-nginx падает на "no endpoints available", пока LB Controller не поднялся — и сам восстанавливается на следующей попытке

На практике для add-on'ов это не потеря надёжности, а сознательный выбор: установки идемпотентны, повторный retry с backoff даёт тот же результат, что и жёсткий гейт, просто не мгновенно — а вот ложное чувство порядка от нерабочей аннотации было бы хуже, чем честный retry.

Для критичных ресурсов (CRD, PV) prune держится выключенным точечно — аннотация argocd.argoproj.io/sync-options: Prune=false на конкретном ресурсе, а не отказ от automated.prune для всего Application: автоматическое удаление должно оставаться включённым везде, где оно безопасно.

09

Промоушен между окружениями

Тег образа продвигается из develop в prod через pull request, меняющий одну строку в overlays/prod/kustomization.yaml (newTag) — не через copy-paste манифеста и не через автоматический апдейтер без ревью.

  • develop: можно доверить ArgoCD Image Updater — новый тег из ECR коммитится в overlays/develop/ автоматически, git остаётся источником правды, просто коммит пишет бот.
  • prod: только ручной PR с ревью. Это единственное решение здесь, где скорость сознательно приносится в жертву аудируемости.

11

Кто следит за самим ArgoCD

ArgoCD Notifications controller шлёт в Slack/webhook события on-sync-failed и on-health-degraded — деградация замечается до того, как о ней узнают из отчёта пользователя. Метрики argocd-* компонентов скрейпит тот же kube-prometheus-stack, который сам разворачивается через этот же механизм — самореференция здесь осознанная: если Argo сломается, это будет видно в дашборде, который он же и поставил.

12

Что происходит при добавлении staging/prod

Это тест того, действительно ли структура масштабируется, а не просто выглядит аккуратно на одном кластере. Добавление второго физического кластера:

  1. Новая папка clusters/prod/ с собственными cluster.yaml / platform-appset.yaml / apps-appset.yaml — platform/ и apps/ не трогаются вообще.
  2. Для по-настоящему N-кластерного роста генератор меняется с git на matrix: пересечение списка кластеров (по label) и списка папок platform/* — тогда даже clusters/<name>/*-appset.yaml перестаёт дублироваться, остаётся один matrix-генератор на весь флот.
matrix generator · один файл на весь флот кластеров
generators:
  - matrix:
      generators:
        - clusters:
            selector:
              matchLabels: { env: production }
        - git:
            repoURL: https://github.com/<org>/terraform-k8s-helm-prometheus.git
            directories: [{ path: gitops/platform/* }]

Новый кластер с правильным label начинает получать весь platform-стек автоматически, без единой правки существующих файлов.

14

Когда выносить gitops/ в отдельный репозиторий

Сейчас — монорепо: gitops/ лежит рядом с environments/ в одном репозитории. Это осознанный выбор под текущий масштаб (один разработчик/homelab), а не временная небрежность. Критерий переезда — не размер кода, а разница в правах доступа: как только появляется команда, которой нужен доступ к gitops/apps/, но не к Terraform/AWS-кредам, монорепо перестаёт быть удобной RBAC-границей.

Структура спроектирована так, что перенос — механическая операция: git subtree split вытаскивает gitops/ в новый репозиторий с сохранением истории, а единственное, что требует правки — значение repoURL в bootstrap-манифестах и ApplicationSet-генераторах. Ни один каталог внутри не переименовывается.

15

Топология: environment↔cluster или environment↔namespace

В разделах 01–14 «окружение» негласно приравнивалось к «кластеру» — папка clusters/develop/ называется по имени окружения, а не по имени физического кластера. Это подходило первой схеме почти без трения. Вторая требует честно разъединить эти два понятия: окружение остаётся точкой в дереве каталогов, а вот что именно оно означает для генератора — кластер целиком или namespace внутри общего кластера — становится параметром, а не архитектурным решением, зашитым в структуру.

Что меняется структурно

Как это выглядит в генераторах

Для namespace-схемы измерение «окружение» переезжает из clusters-генератора в list-генератор, а platform-appset.yaml вообще перестаёт знать про окружения — он остаётся ровно таким, как в разделе 03.

gitops/clusters/homelab/apps-appset.yaml · environment = namespace
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: apps-homelab
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - matrix:
        generators:
          - git:
              repoURL: https://github.com/<org>/terraform-k8s-helm-prometheus.git
              revision: main
              directories: [{ path: gitops/apps/* }]
          - list: # сама ось "окружение" — не кластер, а элемент списка
              elements:
                - env: develop
                - env: staging
                - env: prod
  template:
    metadata:
      name: "{{.path.basename}}-{{.env}}"
    spec:
      project: apps
      source:
        repoURL: https://github.com/<org>/terraform-k8s-helm-prometheus.git
        targetRevision: main
        path: "{{.path.path}}/overlays/{{.env}}"
      destination:
        server: https://kubernetes.default.svc # один и тот же кластер для всех
        namespace: "{{.path.basename}}-{{.env}}"

Кластерная схема из раздела 12 отличается ровно одним: вместо list-генератора по env стоит clusters-генератор с селектором по label — а destination.namespace меняется местами с destination.server. Сам факт, что различие сводится к перестановке двух полей в одном YAML, и есть ответ на вопрос «насколько рабочий подход»: структура выдерживает обе схемы, потому что platform/ и apps/ с самого начала не знали, что такое «окружение» — это знание целиком инкапсулировано в generator'е одного файла.

Что не выдерживает переноса как есть
  • AppProject.destinations в namespace-схеме нужно сузить до паттерна photoapp-* вместо привязки к конкретному кластеру — граница становится мягче, и это нужно компенсировать NetworkPolicy/RBAC внутри кластера, а не считать решённым по умолчанию.
  • IRSA-условие sub в Terraform обязано перечислять namespace явно на каждое окружение — то, что в кластерной схеме была одна роль на контроллер, здесь становится N ролей (или одна роль с более широким, но всё ещё явным списком namespace).

Что выбрать для этого проекта сейчас

CLAUDE.md прямо описывает текущее состояние: один environment (develop), homelab-масштаб, один поддерживающий. При таком масштабе namespace-схема — прагматичный старт: один control plane, один комплект platform-стека, заметно дешевле на AWS-счёте, и весь blueprint из разделов 01–14 применяется почти без изменений — меняется только generator в apps-appset.yaml (list вместо clusters) и добавляются `ResourceQuota`/`NetworkPolicy` по namespace.

Держать путь к кластерной схеме открытым — дёшево: если prod в будущем получит реальных пользователей и деньги на кону, типичное решение большинства команд — гибрид: prod выносится в собственный кластер (изоляция важна там, где она действительно нужна), а develop/staging остаются namespace'ами в одном общем нагрузочном кластере (экономия там, где изоляция не критична). Поскольку измерение «окружение» уже вынесено в один generator одного файла, такая миграция — это правка apps-appset.yaml для одного конкретного env, а не переписывание platform/ или apps/.
